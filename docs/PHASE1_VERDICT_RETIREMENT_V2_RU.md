# Phase 1: выгрузка по живому вердикту OEP, v2

## Что изменилось

В v1 настоящий анализатор уже удалялся, но ждал адрес `retire-boundary` из тестового ELF.
В v2 `retire-trigger=verdict` запускает удаление вслед за собственным выбором OEP.
Адрес точки удаления этому режиму не передаётся. Прежний режим v1 сохранён.
Работа выполнена отдельно, в ветке `phase1-retirement-verdict-v2`; анти-VM отложено.

Последовательность:

1. Phase 1 выбирает текущего кандидата и пишет `oep_candidate_selected`. Сохраняются
   ID кандидата, OEP, PC решения, номер инструкции, эпоха и поколение кода.
2. Выбор происходит в callback перед выполнением гостевой инструкции. Эта инструкция
   выполняется; следующий callback сначала завершает её учёт и снимок регистров.
3. Проверяются актуальность кандидата, эпоха, поколение, номер инструкции и профиль
   одного vCPU. Реальный PC следующей инструкции становится `continuation_pc`.
   В журнал записывается `oep_verdict`; текущая инструкция ещё не включена в трассу.
4. Phase 1 прекращает приём работы, сохраняет дамп, отчёт и manifest. Контроллер
   проверяет экспорт, сохраняет отдельную копию и выдаёт разрешение с nonce,
   ID кандидата и SHA-256 manifest. Ошибка не разрешает продолжение.
5. Плагин вызывает `qemu_plugin_uninstall()` и возвращается из callback.
   QEMU снимает callbacks, вызывает completion; там освобождаются владельцы Phase 1.
   После возврата completion QEMU закрывает модуль. Гость продолжает тот же процесс.

Это не перемотка к OEP: `oep`, `decision_pc` и `continuation_pc` различаются.
Само удаление QEMU асинхронно: после запроса возможен дальнейший прогресс гостя
до завершения удаления. Нулевой промежуток и остановка точно на OEP не заявляются.
Вердикт остаётся эвристическим (`oep_proven=false`).

## Контракт

Автоматический режим использует протокол 2 и capability `verdict_retirement=2`
в sidecar сборки. Он требует QEMU 11.0.1 / plugin API 6. Протокол 1 и capability
`cooperative_retirement=1` сохранены для регрессии v1.

`retire-trigger=verdict` несовместим с `retire-boundary`. Обязателен положительный
`retire-max-insns`: число инструкций, допускаемых до выбора кандидата. Если за
этот бюджет вердикта нет, попытка завершается с кодом 89. Вердикт на последней
допустимой инструкции обрабатывается на следующем входе. В контролируемом профиле
бюджет равен 2048; это параметр теста, а не рекомендация для произвольного образца.
Коды 87/88/90/91 по-прежнему обозначают timeout, отказ протокола, ошибку экспорта
и неподдерживаемый профиль. Повторный запуск неуспешной попытки заблокирован.

Контроллер v2 сверяет событие выбора с вердиктом и capture: ID, PC решения,
trace sequence, эпоху, поколение, фактический PC продолжения. Инвалидация между
выбором и экспортом отвергается. Заранее известный адрес продолжения не нужен.
Контрольный OEP всё ещё проверяется по символу безвредного ELF: текущий unified
профиль не разрешает подставлять произвольный `--binary`.

## Выполненная проверка

Сборка настоящего плагина успешна. Нативные тесты очистки выполнялись под
ASan/UBSan; LeakSanitizer локально отключён из-за ограничений среды. Это не
проверка всей кучи QEMU на утечки. Python integration использует синтетический
исполнитель и сам по себе не доказывает выполнение гостя.

Дополнительно на собранном официальном QEMU 11.0.1 прошли **14 настоящих запусков**:
2 положительные регрессии v1; 6 положительных v2 (задержки 16, 17, 64 × обе
очередности плагинов); deny, stale-permit, bad-digest, disconnect, timeout,
missing-verdict. Положительные запуски подтвердили отсутствие Phase 1 `.so`
в `/proc/<pid>/maps` при живом QEMU, сохранение наблюдателя, PID/starttime,
гостевых буфера, стека и открытого файла. Отказы завершились ожидаемыми кодами
88, 87 или 89 и не дошли до второй точки гостя.

В v2 при одном OEP `0x804c000` реально получены:

| Задержка | Номер инструкции решения | PC решения | PC продолжения |
| --- | ---: | --- | --- |
| 16 | 74 | `0x804c008` | `0x804c009` |
| 17 | 75 | `0x804c009` | `0x804c008` |
| 64 | 122 | `0x804c008` | `0x804c009` |

Это проверяет зависимость триггера от выбора анализатора. Полный новый VM-suite
с systemd/cgroup и финализацией реальной unified-попытки ещё нужно выполнить
на VM пользователя. Принятая ранее VM-приёмка v1 на v2 автоматически не переносится.

## Запуск на VM

Из новой рабочей копии:

```bash
bash scripts/build_run_phase1_verdict_retirement.sh
```

По умолчанию используется `$HOME/.local/opt/taintforge/qemu-11.0.1/bin/qemu-i386`.
Скрипт создаёт новую сборку и новый каталог `workdir/phase1-verdict-retirement-e2e-*`.
Успех: 12 строк `passed`, `status=passed`, `dynamic_trigger_verified=true`,
`runtime_unchanged=true` в итоговом `report.json`; для отказов также `resume_blocked=true`,
для каждого запуска — `tree_empty=true`.

Анти-VM, защита от доступа гостя к служебным FD, отдельное адресное пространство
хостового плагина, абсолютная незаметность и стирание всех следов аллокатора
в эту поставку не входят. Код гостевого упаковщика и гостевые страницы не удаляются.
Следующая граница разработки после VM-приёмки — отделить политику приёма вердикта
и проверку продолжения от контрольного ELF для согласованного профиля образцов.
