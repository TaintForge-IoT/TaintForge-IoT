# M4 execution capsule и актуальная Phase 1

Интеграция основана на полной коллекции восьми рабочих каталогов пользователя.
Контрольные суммы всех 2878 элементов архива и Git bundle проверены.
SHA-256 входного архива: `7ab6bba5c7c2bfdf45c90f1c686be9a00953750a9df311ff683c2e8c1b6a4082`.

## Исходные версии и история

| Составляющая | Использованная версия |
|---|---|
| Актуальная Phase 1 | `6efb3c59686447c588fb21c0fb6352919bba9d7b` |
| Общая база рабочих веток капсулы | `3e74e480eea3e945786aa931690609afb81f5f24` |
| Рабочая M4 | содержимое `taintforge-m4-resources-v1` из коллекции, включая последние исправления |
| Phase 2 | рабочие исходники основного `taintforge`, включая незакоммиченные изменения |

M1–M4 в присланных каталогах были незакоммиченными изменениями поверх одной
старой базы. Поэтому обычный pull обновляет историю, но не переносит рабочие
изменения между каталогами. Для интеграции сначала созданы отдельные Git-снимки
исходников каждого из восьми каталогов. Затем рабочая M4 слита с актуальным
основным каталогом. Оба исходных состояния сохранены родителями merge-коммита;
снимки остальных каталогов также включены в поставляемый bundle.

Сгенерированные файлы `workdir`, старые сборки и удаление 188 отслеживаемых
артефактов не переносились в исходный merge. Старые корневые patch-файлы
сохранены в снимке основного каталога, но не входят в итоговое дерево исходников.
На машине пользователя они останутся на месте.

## Что изменилось в новой Phase 1

От общей базы до `6efb3c5` изменены 108 файлов: 16783 добавленные и 465 удалённые
строки. Основное расширение внесено 10 октября, оптимизации — 11 октября,
ограничения проверки OEP и новые Python-сценарии — 22 октября.

| Изменение Phase 1 | Значение для Phase 2 и капсулы |
|---|---|
| Захват памяти до исполнения инструкции кандидата | Исторический образ кандидата нельзя считать текущим состоянием продолжающегося процесса |
| Кеши provenance и сокращённый сбор вспомогательной трассы | Новые владельцы должны освобождаться при retirement; полный сбор сохраняется в M4-профиле |
| `ir_environment`, моделирование файлов и отображений | Это модель для IR, отдельная от настоящей файловой системы и сети Phase 2 |
| `ir_oep_verify` | Доказывает только ограниченные свойства конкретного фрагмента при заданной политике входов |
| Concolic для stdin и файлового окружения | Даёт ограниченный вариант входа с обязательным реальным повторным запуском; не восстанавливает процесс |
| Контролируемый корпус, ELF rebuild и cold-run | Проверяет отдельный сценарий захвата/перезапуска; это не доказательство общего checkpoint/resume |

Рабочий backend собирается из `unpacker/test`. Корневой `unpacker` содержит
другую, более старую реализацию; подменять ею выбранную сборку нельзя.
`unpacker/mvp/source` остаётся относительной ссылкой на `../test`.

## Захват, решение и продолжение

| Момент | Что он означает |
|---|---|
| Наблюдение кандидата | Инструкция кандидата ещё не исполнена; можно сохранить ранний образ страниц |
| Выбор кандидата | Ретроспективное эвристическое решение после заданной задержки |
| Retirement boundary | Следующая инструкция после решения; фиксируется текущий continuation PC |
| Observer HOLD | Независимый наблюдатель подтверждает выгрузку и удерживает продолжаемый процесс |

В интегрированной M4 разрешён экспорт на границе retirement, использующий режим
`tf-capture=exit` по умолчанию. Название `exit` здесь обозначает стратегию
финализации; при retirement экспорт выполняется до выгрузки плагина, а не после
завершения гостя. Совмещение `tf-capture=entry` и `retire-*` отклоняется в native
конфигурации до регистрации callbacks. Это покрыто нативным тестом.

Режим `entry` сохранён для самостоятельного анализа Phase 1. В `Phase1Run`
добавлены `tf-capture` и `tf-max-capture-bytes`, чтобы Phase 2 могла явно выбрать
этот режим для отдельной диагностической попытки. Строгий M3/M4 CLI по-прежнему
не допускает произвольную замену настроек retirement.

Реальный тест на QEMU 11.0.1 показал разницу: у одного и того же benign ELF
ранний образ получен на sequence 57, финальный — на sequence 8391. Оба экспорта
проверены по хешам; программа в обоих запусках завершилась с `CAPSULE_OK`.
Поле согласованности остаётся `best_effort_no_backend_safepoint`.

## Порядок retirement и освобождение ресурсов

Сохранён порядок M4: завершение наблюдений предыдущей инструкции → фиксация
continuation → запрет новых наблюдений → экспорт и проверка его хеша → permit →
асинхронный uninstall → callback завершения удаления → освобождение владельцев →
независимая проверка отсутствия mappings → разрешение продолжения.

При слиянии отдельно сохранён вызов `tf_retire_verdict` при выборе кандидата.
Новая инструкция не добавляется в трассу как уже выполненная до проверки
retirement. Совместимость новой Phase 1 с API ≥7 не расширяет контракт M4:
cooperative retirement остаётся ограничен QEMU 11.0.1/API 6.

Объединены source lists сборки: `ir_environment`, `ir_concolic`, `ir_oep`,
`phase1_retire` и `phase1_resources` компилируются вместе. Все проектные индексы
регистров в новых native-модулях и тестах приведены к `DTA_REG_*`, чтобы они не
совпадали с enum из системного `ucontext.h`.

Для concolic выделен `tf_concolic_finish`: он закрывает отчёт до фиксации
экспорта, но оставляет память до завершения удаления callbacks. Destructor затем
освобождает структуры без изменения отчёта. Указатель включён в проверку
оставшихся владельцев. Тест реального destructor проверяет ранние candidate
структуры, concolic-файл, повторную финализацию, стабильность SHA-256 отчёта после
освобождения и нулевой остаток явных M4-аллокаций.

Новые кеши provenance освобождаются штатным destructor новой Phase 1.
Принудительное включение `phase1_alloc.h` сохранено для всех модулей сборки.
Ledger учитывает явные проектные аллокации; внутренние аллокации внешних библиотек
по-прежнему не объявляются полностью отслеживаемыми или гарантированно стёртыми.

## Concolic и следующая работа Phase 2

Новые `run_concolic_file.py` и `run_concolic_environment.py` сохранены. Их
самостоятельный запуск использует прямой subprocess/QEMU runner и не является
новым режимом изоляции M4. В этой интеграции они не подключаются автоматически
к защищённому retirement-маршруту.

Следующий отдельный шаг — исполнить concolic-сбор внутри явно связанной
диагностической попытки Phase 2, сохранить результат, материализовать производное
окружение и проверить его новой полноценной попыткой. Идентификаторы инструкций
и ресурсов остаются локальными для запуска; их нельзя механически объединять
между исходным и повторным запуском. После удаления Phase 1 её DSE не продолжает
работать внутри уже освобождённого плагина.

Профиль concolic stdin ограничен одним прочитанным байтом и static i386 ET_EXEC.
Файловый профиль ограничен одним файлом до 1 MiB, чтением до 4096 байт и до 16
изменяемых смещений. Подтверждение ветвления относится к проверенному префиксу,
а не к произвольному суффиксу исполнения.

`ir_oep_verify` не подключён автоматически к эвристическому выбору OEP. Даже
результат `UNIQUE_ON_FRAGMENT` не делает кандидат доказанным OEP. Поэтому
`oep_proven`, `exact_oep_cutover` и `fuzzing_ready` не повышаются.

## Исправление упаковки MVP

В исходной `6efb3c5` семь хешей в `unpacker/mvp/manifest.json` не соответствовали
исходникам после оптимизаций 11 октября. Это останавливало проверку пакета в
`cu_runner`/`cv_runner`. Manifest пересчитан по итоговым исходникам, включая новые
retirement/resource-файлы; проверка целостности не отключена.

## Проверки и ограничения

Проверены сборка плагина для API 6, пять native-наборов OEP/control-flow,
M2.2 native regressions, 489 разных Python-тестов, реальные загрузка и snapshots
QEMU 11.0.1, а также два режима экспорта на benign ELF. Подробные результаты и
точные границы проверок находятся в `VALIDATION.json` поставки.

Один Python-тест требует `tests/fixtures/test_stat_qemu_returns.log`: этот
неотслеживаемый `.log` не попал во входной архив. Он не переписан синтетическими
данными. Два первоначально пропущенных QEMU-теста затем выполнены с явно
заданным `TF_OBSERVER_QEMU`.

AddressSanitizer и UBSan проверяют реальный destructor; LeakSanitizer в этой
среде не может читать `/proc/<pid>/task`, поэтому отключён через предусмотренную
настройку `TF_RETIRE_LSAN=0`. Полный handoff/E2E с IPC и systemd/cgroup здесь
не подтверждён: создание Unix-сокетов запрещено средой. В пакет включён
`verify_on_host.sh` для повторного полного M4 acceptance на машине пользователя.

Остаётся прежний scope: benign lab, static i386, один процесс и поток,
неподтверждённая защита control channel, отсутствие полного process checkpoint.
Пределы M4 не расширялись до 40 GiB: native-парсер ограничен 4 GiB, текущая
Python-политика — 1024 MiB, штатный analysis budget — 512 MiB.

## Установка

`install_integration.py --repo ~/taintforge --all-worktrees` проверяет исходные
хеши, импортирует bundle в локальный Git, сохраняет снимки восьми каталогов,
создаёт резервную копию меняемых файлов и всех исходных Git indexes. Затем
обновляет исходники и продвигает восемь существующих веток на общий merge-коммит.
Все продвижения являются fast-forward; rebase и сетевой push не выполняются.
Без `--all-worktrees` обновляется только выбранный каталог.

Изменения `workdir`, не относящиеся к исходникам, и соответствующие записи index
сохраняются. Новые изменения исходников после коллекции останавливают установку
до замены файлов. Есть read-only `--check` и восстановление `--restore BACKUP`;
восстановление также проверяет, что установленный код/index не менялись.

После установки нужна новая сборка плагина и новые execution attempts. Старые
runtime bundles, build manifests и acceptance относятся к прежним бинарникам.
