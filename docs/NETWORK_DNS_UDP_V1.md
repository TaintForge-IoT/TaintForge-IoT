# DNS и UDP: сетевой контур фазы 2

Этот блок дополняет существующий TCP record/import/replay. Изменения относятся
к сетевым сервисам и prebuilt runner фазы 2. Файлы анпакера, контракт фазы 1,
общий launcher и механизмы памяти здесь не изменяются.

## Режимы

| Режим runner | Источник ответа | DNS | UDP |
|---|---|---|---|
| `--network record` | Указанный в политике upstream | Запись запроса и ответа, UDP и TCP | Одна дейтаграмма запроса и одна ответа |
| `--network replay` | Проверенная копия ReplayStore | Восстановление текущего transaction ID и регистра вопроса | Точное сопоставление байтов дейтаграммы |
| `--network controlled` | Локальная модель | Явные `dns_records`, ответы помечены как synthetic | Прежнее наблюдение неизвестного UDP; произвольный UDP-сервис не моделируется |
| `--network none` | Нет сетевых сервисов | Нет | Нет |

В record и replay неизвестные назначения не получают общего перенаправления
на заглушку. Прямой внешний маршрут гостя закрыт. В record к upstream обращается
host broker, причём его адрес и порт заданы явно. В replay обращений к upstream
нет; неизвестный DNS-вопрос получает синтетический `SERVFAIL`, неизвестный
UDP-запрос остаётся без ответа, оба случая попадают в журнал.

DNS TCP fallback обслуживается отдельным TCP-сервисом: клиент видит `TC=1`
в ответе UDP и сам повторяет запрос по TCP. Forwarder не заменяет усечённый
ответ незаметным рекурсивным запросом.

## Быстрая приёмка

Из корня проекта, после применения предыдущих патчей TCP capture и sandbox:

```bash
PYTHONPATH=. python scripts/run_dns_udp_replay_e2e.py \
  --out "workdir/dns_udp_local_$(date +%Y%m%d_%H%M%S)"
```

Это настоящий статически собранный C-клиент и реальные loopback-сокеты. Для
сборки нужны Linux x86-64, GCC и статическая libc. Клиент получает IP по домену,
проходит DNS UDP → TCP fallback, затем TCP и UDP обмены. После записи все
mock upstream-серверы останавливаются. Импортированный набор воспроизводит
тот же результат, неизвестное имя проверяется отдельно.

Локальный вариант проверяет DNS через собственный небольшой resolver fixture.
Он также подготавливает и проверяет prebuilt replay-сессию, но гостя внутри
namespace не запускает. `sandbox_executed: false` в отчёте отражает это.

Полная приёмка на VM:

```bash
sudo -v &&
PYTHONPATH=. python scripts/run_dns_udp_replay_e2e.py \
  --out "workdir/dns_udp_vm_$(date +%Y%m%d_%H%M%S)" \
  --sandbox
```

Этот вариант дополнительно выполняет **две** изолированные итерации публичного
prebuilt runner: сначала record, затем replay после остановки upstream. Он
проверяет libc `getaddrinfo`, `resolv.conf` с loopback nameserver, явно заданный
DNS-адрес, DNS/TCP fallback и DNAT для обоих транспортов C2. Адрес C2 клиенту
не передаётся: он знает только домен и порты сервисов.

Нужны обычные зависимости prebuilt runner: sudo, iproute2, iptables, unshare,
mount/chroot, strace и поддержка namespaces в ядре. Каталог `--out` должен быть
новым. При ошибке нет успешного `report.json`; диагностические артефакты
созданных итераций сохраняются. Успешная VM-приёмка содержит
`sandbox_executed: true`, `record_executed: true` и `replay_executed: true`.

## Политика записи

Пример: `examples/network_dns_udp_record_local.json`. Это конфигурация для
локальных mock-серверов, а не автоматически работающие внешние адреса.
Политика помещается в `template/config/network_policy.json`. Существующие
команды `run_synthesis_loop.py` и `run_prebuilt_iteration.py` принимают
`--network record`.

Каждый сервис содержит:

- `service_type`: `tcp` или `udp`;
- `remote_ip`, `remote_port`: исходное назначение, видимое гостю;
- `bind_ip`, `bind_port`: локальный listener; backend назначает фактические
  свободные порты в своей топологии;
- `upstream_ip`, `upstream_port`: явно заданный источник записываемого ответа;
- `protocol_hint: "dns"` для DNS-сервиса;
- `domain` для C2, если при replay нужно проверить соответствие домена его IP.

Для DNS нужны два сервиса с одинаковым исходным адресом и портом: UDP и TCP.
Для другого DNS-адреса, включая `127.0.0.1` или `127.0.0.53`, добавляется
отдельная пара. `resolv.conf` и `nsswitch.conf` входят в подготовленный rootfs.
Record backend перенаправляет loopback DNS к host broker; replay обслуживает
loopback DNS внутри namespace.

`recording.capture_kind` различает `local_test` и `live`. У live должен быть
`live_capture_acknowledged: true`. DNS upstream задаётся IPv4-адресом, а не
доменом; для live он должен быть глобально маршрутизируемым. Для обычного C2
сохраняется прежняя live-политика: исходный и upstream endpoint совпадают.
В local_test upstream ограничен loopback/private адресами. Эти параметры не
выдают гостю прямой доступ в Интернет.

Ограничения записи сообщений задаются явно: `max_exchanges` (по умолчанию 256),
`max_pending` (16), `timeout_seconds` (5) и `quiet_seconds` (0.05). Последнее —
окно наблюдения за дополнительным UDP-ответом. Это не доказательство отсутствия
поздних пакетов. Превышение лимита параллельных обработчиков приводит к отбрасыванию
пакетов. TCP C2 продолжает использовать собственные ограничения прежнего broker.

Для синтетического DNS в controlled к каждому DNS-сервису добавляется, например:

```json
"dns_records": {"c2.example": ["198.51.100.10"]}
```

Поддерживаются A/AAAA-ответы, неизвестное имя даёт NXDOMAIN. Эти ответы имеют
`response_origin: "synthetic"`; они не выдаются за запись upstream. Старый
catch-all logger режима controlled остаётся отдельным механизмом наблюдения;
record/replay его не используют.

## Capture → проверенный replay bundle

UDP и DNS публикуются как `network-message-v1`: `session.json`, `events.jsonl`,
`request.bin`, `response.bin`. Capture содержит оба исходных endpoint, run/session
ID, тип записи, размеры, хеши и статус. DNS TCP capture хранит DNS-сообщение без
двухбайтового транспортного префикса; replay формирует префикс заново.

Существующий TCP формат сохранён. Импортёр выбирает формат по метаданным.
Timeout, незавершённая запись, несовпадение хеша или лишний UDP-ответ в окне
наблюдения не становятся успешной записью ReplayStore.

Для импорта всей итерации:

```bash
PYTHONPATH=. python scripts/import_network_recording.py \
  --capture-dir workdir/record_session/iterations/0000/run/logs \
  --policy workdir/record_template/config/network_policy.json \
  --out workdir/network_bundle
```

Команда сверяет capture с политикой: исходный endpoint, upstream, run ID и тип
записи. Все сессии проверяются в промежуточном каталоге. Готовый bundle появляется
только после проверки всего набора; существующий каталог не заменяется.

Результат:

- `replay_store/`: проверенный набор обменов;
- `network_policy.json`: политика replay без upstream и recording options;
- `import_report.json`: квитанции импорта, хеш политики и `store_sha256`.

Скопируйте политику bundle в **новый** replay template и передайте
`--network replay --replay-store workdir/network_bundle/replay_store` при
создании новой synthesis-сессии. Уже связанную record-сессию не переводят в
replay изменением её файлов. Как и раньше, runner проверяет привязку store и
создаёт отдельную проверенную копию для попытки.

Одиночный capture можно импортировать прежней командой `scripts/replay_store.py
import-capture`. Повтор одинакового обмена не меняет store; другой ответ для
того же ключа отклоняется. Bulk import не поддерживает конкурирующих писателей
в один destination.

## Семантика DNS и границы профиля

DNS-ключ не включает transaction ID и регистр имени. Тип/класс вопроса,
значимые query flags и поддерживаемый EDNS сохраняются. При воспроизведении
восстанавливаются ID и регистр текущего вопроса, а записанные RDATA, TTL и flags
ответа остаются прежними. Ссылки DNS compression сохраняют свои смещения.

Поддерживается один несжатый вопрос класса IN, стандартный QUERY, необязательный
EDNS(0) без options. Проверяются границы пакета, вопрос, ID, записи A/AAAA/CNAME.
Другие RDATA сохраняются как байты; криптографическая проверка DNSSEC не заявлена.
Профиль не включает DNS transfers, EDNS cookies/options, DoH, DoT и IPv6 transport.
Сама AAAA-запись при DNS replay сохраняется, но C2 transport этой версии — IPv4.

TTL фиксируется записью, а не уменьшается по настенным часам. Различающиеся
ответы, в том числе изменившийся TTL, для одного ключа дают конфликт при импорте.
Новая попытка создаёт новые сервисы и новый guest process; состояние внешнего
DNS-cache или произвольного persistent guest эта версия не сбрасывает.

Если у C2 задан `domain`, при подготовке replay требуется успешный полный
DNS-ответ, связывающий имя с настроенным `remote_ip`, при необходимости через
CNAME. Адрес из постороннего additional RR, ошибочного или усечённого ответа
сам по себе такую связь не подтверждает.

**Назначения C2 пока должны быть перечислены в политике.** DNS forwarding
разрешает домен, но не добавляет автоматически разрешение для каждого нового
IP из ответа. Для домена с несколькими рабочими адресами нужны соответствующие
C2 endpoints и их записи. Обнаружение новых адресов и обновление политики —
отдельный шаг synthesis, а не скрытое расширение сети во время replay.

Обычный UDP ограничен независимыми транзакциями «одна дейтаграмма → одна
дейтаграмма». Для каждого запроса broker создаёт отдельный upstream socket:
ответы параллельных клиентов не смешиваются. Сессии, зависящие от постоянного
source port, push-пакеты, несколько ответов, streaming и многошаговые протоколы
требуют отдельной модели. Нулевые дейтаграммы поддерживаются. Replay не
гарантирует порядок завершения конкурентных независимых транзакций.

## Проверки и следующий этап

Тесты проверяют DNS ID/case, повреждённые пакеты, negative/truncated replies,
TCP framing, пустой UDP, таймаут, несколько ответов, конкурентные запросы,
синтетический DNS, правила backend и реальный C-клиент с выключенным upstream.
Проверка генерации iptables-команд не заменяет VM-приёмку их исполнения.

В среде разработки локальные сценарии доступны, но iptables отсутствует,
а привилегированное выполнение ограничено. Поэтому окончательная приёмка
namespace, loopback DNAT и libc resolver выполняется командой `--sandbox` на VM.
После неё следующий блок — Execution Capsule + Memory Provenance + Residue
Oracle, с отдельным согласованием границы интеграции с разработчиком фазы 1.
