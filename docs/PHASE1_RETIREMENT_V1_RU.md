# Phase 1: исправления владельцев ресурсов и cooperative retirement v1

Дата: 1 октября 2026. Ветка: `phase1-retirement-v1`.

По новой инструкции пользователя исправления Phase 1 выполнены самостоятельно в отдельной ветке. Основа — полный набор исходников `unpacker/test` из `main` `3e74e480eea3e945786aa931690609afb81f5f24`, использованный в аудите, плюс ранее принятая интеграция Capsule. Старый аудит и его эталонные хеши сохранены как история; они не объявляются эталоном изменённого кода.

Результат — реализация для приёмки на контролируемом ELF. Полный маршрут через Unix-сокеты, systemd/cgroup и фактическую выгрузку нового Phase 1 требует запуска VM-suite. Это ещё не разрешение запускать произвольные образцы в боевом режиме.

## Порядок передачи управления

1. Phase 1 выбирает текущего кандидата своей существующей эвристикой и публикует `oep_verdict`. Он содержит ID кандидата, OEP, PC/trace решения и будущую границу продолжения. Статус — `selected_candidate`, `oep_proven=false`.
2. Первый observer удерживает гостя и сохраняет доказательство, что Phase 1 ещё отображён. После CONTINUE гость доходит до отдельного `phase1_retire_boundary`.
3. На этой границе Phase 1 проверяет, что кандидат существует, не устарел и относится к текущей эпохе. Завершает запись предыдущей инструкции, запрещает новые аналитические callbacks и явно читает гостевую память в instruction callback с правом чтения регистров. Инструкция продолжения в экспорт ещё не записывается как выполненная.
4. Host-сериализация формирует report, завершённый events и capture manifest. Чтение гостя больше не скрыто внутри `write_report()`. Экспорт завершается до ожидания permit.
5. Независимый permit-worker сверяет identity, порядок, вердикт, SHA-256 всех артефактов, полный capture и присутствие выбранного кода. Политика этого профиля разрешает только известный адрес функции закреплённого тестового ELF. Он сохраняет отдельную копию экспорта, синхронизирует её, повторяет проверку и отправляет `RETIRE <nonce> <candidate_id> <manifest_sha256>`.
6. Только после точного разрешения Phase 1 сообщает `uninstall_requested`, вызывает `qemu_plugin_uninstall()` для собственного ID и возвращается. Callback userdata ещё живы. Новые обращения к аналитике отвергаются.
7. QEMU выполняет свою асинхронную процедуру снятия callbacks и вызывает completion. Там Phase 1 сообщает `callbacks_removed`, освобождает своих host-владельцев, отправляет `resources_released`, закрывает канал и возвращается. Здесь нет чтения гостя и ожидания контроллера.
8. QEMU закрывает модуль после возврата из completion. На второй удержанной точке внешний observer проверяет отсутствие Phase 1 `.so`, присутствие своего модуля, тот же PID/start time и неизменные стек/FD. Лишь после этой проверки разрешается следующее CONTINUE. Финализатор заново проверяет сохранённые доказательства.

Permit-worker и observer-worker — разные процессы. Поэтому ожидание Phase 1 своего разрешения не зависит от того, успел ли observer войти в следующий callback. Загрузка Phase 1 до или после observer входит в VM-suite.

Возврат из `uninstall` сам по себе не считается остановкой гостя до completion: QEMU обрабатывает запрос асинхронно. Ограниченный участок между двумя контрольными точками принадлежит известному тестовому ELF. Переход к дальнейшему выполнению разрешается на второй точке после внешней проверки. Это не доказательство мгновенного отсечения произвольного кода на точном OEP.

Таймаут выбора новой стадии не является отдельным разрешением на удаление. Сама существующая эвристика Phase 1 использует `selection_delay`; её результат остаётся эвристическим. Отсутствие вердикта на границе немедленно прерывает попытку. Ретроспективный выбор при обычном atexit разрешения retirement не создаёт. EIP не переписывается, отката к OEP нет.

## Исправления аудита и область очистки

- **F01/F05:** реализован opt-in live-интерфейс; гостевой capture отделён от host-сериализации и release. Старый atexit больше не используется как середина живого выполнения.
- **F02:** `pages` имеет value destructor, освобождающий `page_t` и `wbitmap`; guest munmap удаляет элемент через него. Полный release уничтожает и оставшиеся элементы. Гостевые mappings не освобождаются этим destructor.
- **F03:** последняя `g_oep_scoring` освобождается; заимствованный `g_selected_candidate` сбрасывается до уничтожения списка.
- **F04:** два function-local TLS `GByteArray` перенесены в управляемый `PluginVcpuState`. Предыдущие регистровые байты обнуляются перед повторным чтением, live-буферы освобождаются при release.
- **F08:** одна idempotent-процедура release используется после частичной установки, при обычном exit и после подтверждённого снятия callbacks. Ссылки обнуляются. Callback userdata живут до completion. Модель FD освобождает metadata, но не закрывает FD гостя. Таблица сетевой модели также получает value destructor, включая замену записи при переиспользовании номера FD.
- **F06 — частично:** проверяется перечень верхних указателей-владельцев, публикуются числа освобождённых page/bitmap/register buffers и объём явно выполненного обнуления в этих ограниченных путях. Это **не полный allocator ledger** и не независимое доказательство отсутствия всех allocations. `all_phase1_allocations_released=false`, `allocator_residue_verified=false`, `all_bytes_zeroed=false`.
- **F07 — остаётся:** отдельного общего byte budget для всего heap Phase 1 и архива здесь не добавлено. Новый профиль обязательно использует ранее проверенные внешние cgroup-лимиты. Общий allocator/budget и полноценный residue oracle требуют следующего изменения.

Обычные `free/g_free` для trace, provenance, DCFG, IR/Z3/Capstone и строк освобождают владельцев, но не гарантируют обнуление всех старых копий в allocator, стеке, libc или общих библиотеках. Сохранённый экспорт намеренно остаётся доступным. `owner_roots_remaining=0` — ограниченный внутренний отчёт, а отсутствие `.so` — отдельное внешнее наблюдение. Эти сведения не приравниваются к очистке всего адресного пространства.

## Запуск

Нужны Linux, динамический QEMU **11.0.1 / API 6**, compiler/binutils, pkg-config и development-файлы GLib, Capstone, Z3, а также зависимости уже работающего unified Capsule/systemd/cgroup v2. Версионный барьер не ослаблен ради системного QEMU 11.1.1.

После применения патча и перехода в отдельную рабочую копию:

```bash
bash scripts/build_run_phase1_retirement.sh
```

По умолчанию выбирается уже использованный `$HOME/.local/opt/taintforge/qemu-11.0.1/bin/qemu-i386`. Можно передать другой путь к той же версии первым аргументом, новый каталог отчёта — вторым. Плагин собирается в уникальном каталоге `build/retirement-v1/build.XXXXXXXX/`. `sudo -v` вызывается перед VM-suite.

Низкоуровневый единичный запуск через unified CLI использует `--capsule-phase1-retirement` с `--network none --max-iterations 1 --max-steps 1`; произвольный `--binary` и свободные analysis options этим профилем не принимаются. Режим `--capsule-lifecycle` по-прежнему относится к старому тестовому owner.

VM-suite проверяет:

| Сценарий | Ожидаемый результат QEMU |
| --- | --- |
| Phase 1 загружен первым / observer первым | 0, подтверждённые export, removal, `.so` absent, сохранённый guest oracle |
| DENY, устаревший nonce, неверный digest, disconnect | 88, продолжения после границы нет |
| Нет permit до deadline | 87, продолжения нет |
| Phase 1 не успел выдать вердикт | 89, запрос удаления не выполняется |

Во всех отрицательных случаях попытка становится terminal; повторный resume не выполняет гостя заново. Suite проверяет очищенное дерево cgroup и неизменность выбранных QEMU/`.so`/sidecar. Выход самого гостя 0 без доказательств удаления не засчитывается.

## Фактическая локальная проверка

Полная сборка 27 C-файлов проходит. 59 проверок существующей и новой unified-интеграции проходят. Ещё 7 тестовых методов проверяют native-протокол, владельцев и контракты, включая несколько сценариев в каждом методе. ASan/UBSan проходят для заполненного, частичного и повторного release.

Из исходного release собран настоящий QEMU 11.0.1; его публичный header совпадает с закреплённым SHA-256. На нём проверены: обычное исполнение тестового ELF с настоящим Phase 1; реальный выбор ожидаемого OEP и целостность экспорта; live capture до отказа недоступного контроллера; отказ без вердикта до экспорта/удаления. После отказов гость не записывает `between`/`after`.

Ограничения среды проверки: создание Unix-сокетов запрещено, а LeakSanitizer не может читать `/proc/<pid>/task`. Поэтому native protocol tests используют разрешённый socketpair с подменой только точки входа транспорта; локальный ASan запускается с `TF_RETIRE_LSAN=0`. Полный socket handshake, QEMU uninstall/dlclose нового плагина вместе с observer и весь systemd-suite **здесь не подтверждены**. На VM helper включает LeakSanitizer по умолчанию и запускает реальные восемь сценариев. После успешного отчёта принимается именно этот ограниченный профиль; общая боевая готовность и одиннадцать последующих направлений остаются отдельными этапами.
