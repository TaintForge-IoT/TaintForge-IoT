# Фаззинг после одной распаковки

Режим `warm` запускает исходный ELF и Phase 1 **один раз на живую кампанию**.
После экспорта и подтверждённого retirement QEMU доходит до первого открытия
выбранного входного файла и становится родительским шаблоном. AFL++ начинает
свою кампанию только после готовности этого шаблона. Минуты подготовки не
расходуют временной бюджет `afl-fuzz -V`.

На каждую мутацию создаётся дочерний процесс **из распакованного QEMU**.
Он продолжает тот же гостевой syscall с теми же регистрами, стеком, heap и
отображениями памяти. Phase 1 в дочернем процессе уже удалена. Родитель
остаётся перед открытием входа. Память Linux наследует через copy-on-write:
отдельной полной копии 40 ГиБ для каждой мутации не создаётся. Дочерние
исполнения последовательные; после завершения или таймаута процесс собирается
через `waitpid`.

## Последовательность

1. Одна сессия unified pipeline поднимает обычный M4 service и QEMU.
2. Phase 1 выбирает текущую точку продолжения, завершает экспорт, снимает
   callbacks, освобождает учтённые ресурсы и выгружается.
3. Независимый observer проверяет retirement, отсутствие модуля в `/proc/maps`
   и сохранность состояния на HOLD 2. `RESUME 2` разрешает checkpoint.
4. Перед первым `open`/`openat` выбранного абсолютного пути backend завершает
   служебный поток observer. Сам `fork` происходит после возврата plugin
   callbacks, через `fork_start`/`fork_end` QEMU, вне их обхода.
5. Проверяются унаследованные дескрипторы, отсутствие поддерживаемых профилем
   разделяемых гостевых отображений, cwd и текущий RSS. Выполняется
   `malloc_trim(0)`, затем проверяется заданный предел RSS.
6. Контроллер сохраняет **файловое состояние в точке checkpoint**, включая
   изменения, которые успела сделать подготовка. Это отличается от исходного
   rootfs до распаковки. `/proc`, `/sys`, `/dev` и служебные mounts не копируются.
7. Для мутации контроллер восстанавливает это дерево, подставляет вход и
   очищает карту покрытия, сохраняя её inode. Только затем родитель создаёт
   следующего ребёнка. Регистры гостя не подменяются результатом guest `fork`:
   это внутреннее клонирование backend, а не syscall, выполненный образцом.
8. Покрытие включается после успешного чтения входа. Результат сохраняется с
   SHA-256 входа, карты и базового дерева. AFL++ получает карту гостя 64 KiB.
9. В конце кампании шаблон закрывается, pipeline проверяет retirement и очистку
   service/cgroup. Родитель не выдаётся за завершившийся обычный guest:
   `guest_completed=false`; результаты payload относятся к дочерним попыткам.

## Установка

Архив содержит накопительные изменения относительно M4 integration v1 и
совместим с неизменёнными файлами предыдущего AFL file MVP v1. Установщик
проверяет хеши, сохраняет резервные копии и откатывает частичную установку.
При локальном расхождении он ничего не заменяет. Коммитов и push нет.

```bash
cd "$HOME/Downloads"
unzip taintforge_afl_post_retirement_v2.zip
python3 taintforge_afl_post_retirement_v2/apply.py --repo "$HOME/taintforge" --check
python3 taintforge_afl_post_retirement_v2/apply.py --repo "$HOME/taintforge"

cd "$HOME/taintforge"
bash scripts/build_afl_warm_qemu.sh
bash scripts/build_run_afl_warm.sh \
  "$HOME/.local/opt/taintforge/qemu-11.0.1-warm/bin/qemu-i386" \
  "$PWD/workdir/afl-warm-acceptance" \
  /usr/bin
```

Сборщик использует отдельный каталог QEMU и отдельный install prefix. Нужны
обычные зависимости сборки QEMU, `git`, `ninja`, `pkg-config`, C-компилятор,
`binutils` и `rg`. Если исходники QEMU 11.0.1 уже есть, их путь и отдельный
prefix можно передать двумя аргументами `build_afl_warm_qemu.sh`. При изменённых
исходниках автоматическая правка отклоняется; для проверки есть
`experiments/afl_file/qemu/qemu-changes.patch`.

Обычный QEMU 11.0.1 без private warm ABI не подходит. Проверка выполняется до
подготовки кампании. Первая фаза также пересобирается: её учётный лимит памяти
теперь допускает большой подготовительный этап.

Полный результат на хосте: `workdir/afl-warm-acceptance/e2e/acceptance.json`.
Команда требует systemd, cgroup v2, sudo и mount/PID/network namespaces.
Она проверяет именно M4 и не заменяет недоступный M4 компонентным тестом.

## Запуск своей файловой кампании

`python3 -m scripts.run_afl_file prepare` теперь выбирает `warm` по умолчанию.
Ему передаются существующие ELF, Phase-1 plugin, patched QEMU, каталог seeds,
абсолютный гостевой путь и новый каталог `--out`. `run --out` запускает одну
подготовку и затем AFL++. Старый медленный режим доступен только явным
`prepare --mode fresh`.

| Параметр prepare | По умолчанию | Назначение |
|---|---:|---|
| `--bootstrap-seconds` | 1200 | Ожидание распаковки, retirement и checkpoint |
| `--campaign-seconds` | 3600 | Подготовленный предел длительности фаззинга |
| `--timeout-ms` | 2000 | Время одного дочернего payload |
| `--memory-mib` | 65536 | Жёсткий общий предел service/cgroup, swap выключен |
| `--analysis-mib` | 49152 | Лимит явно учитываемых аллокаций Phase 1 |
| `--max-rss-mib` | 2048 | Максимальный текущий RSS родителя перед fork |
| `--max-input` | 4096 | Максимум байтов одного входа |

Лимиты 64/48 ГиБ не являются предварительным выделением такой памяти. Их можно
снизить для небольших образцов. Отдельный RSS-порог запрещает начинать forkserver,
если после retirement осталась большая резидентная память. Это проверка текущего
RSS, а не `ru_maxrss` и не максимума, достигнутого во время анализа.
`malloc_trim` освобождает свободные arenas glibc; он не исправляет утечки или
живые неучтённые объекты. Если Phase 1 всё ещё удерживает 40 ГиБ, запуск завершится
с `phase1_resident_memory_not_released`; освобождение этих объектов нужно исправить
в самой Phase 1. Этот механизм не объявляет всю её память доказанно освобождённой.

В `run` параметр `--seconds` ограничивает уже сам AFL++ и должен быть не больше
подготовленного `--campaign-seconds`. По окончании шаблон уничтожается. Дискового
снимка CPU/RAM и восстановления кампании после перезапуска процесса здесь нет:
новая живая кампания требует новой первоначальной распаковки.

## Границы текущей базы

- Статический i386 ET_EXEC, один guest task/vCPU, сеть `none`, один выбранный
  абсолютный путь. Форматы и архитектуры основного M3-профиля не расширялись.
- Checkpoint разрешён только после retirement и **перед первым открытием входа**.
  Если файл открыт до разрешения, запуск отклоняется. Если программа открывает
  его другим относительным именем либо получает содержимое через другой канал,
  профиль не гарантирует подстановку; готовность не объявляется до checkpoint.
- Поддерживаются `open`/`openat` и последующие `read`/`pread64`. Прямое чтение входа
  через `mmap`, `dup` и передача дескриптора не поддерживаются.
- Унаследованные открытые файлы/сокеты, IPC и таймеры, которые этот профиль не
  умеет сбрасывать, отклоняются. Новая реализация не восстанавливает произвольное
  состояние ядра. Требуется cwd `/`; rootfs копируется последовательно на диске.
- PIDs детей отличаются, время и случайность хоста не заморожены. Повторяемость
  контролируемого ELF проверена; для произвольного образца её нужно измерять.
- Ошибки исполнителя, неподдерживаемое состояние и таймаут останавливают кампанию,
  а не маскируются под найденные guest crashes. Полноценная классификация сбоев,
  oracle, replay, сетевые входы, env и DSE остаются отдельными задачами.
- Защищённый control channel и устойчивость к враждебному образцу по-прежнему не
  заявлены. Тестовые ELF безвредны. Эти ограничения унаследованы от текущей капсулы.

## Проверки в комплекте

`validation/verification.json` перечисляет фактически выполненные проверки.
Компонентный тест использует настоящий patched QEMU 11.0.1 и AFL++, однако
не выдаёт подготовку учебного ELF за реальную Phase 1/M4.

Выполнены проверки разных карт покрытия, одинаковых карт повторных входов,
памяти дочерних попыток, файлового маркера, единственного выполнения подготовки,
RSS-порога, раннего открытия входа, открытого FD, потери контроллера и таймаута.
Дополнительно синтетический M4-тест проверяет всю финализацию и portable evidence,
включая запрет на пропуск независимого события `module_unmapped`.

Полный M4-прогон и образец с реальным пиком 40 ГиБ в текущей среде не выполнены.
В комплекте есть отдельная хостовая проверка; её результат нельзя считать
успешным до получения `status=passed` на подходящем хосте.
