**Execution Capsule: отключение тестового анализатора и освобождение его памяти, v1.**

Этот комплект — следующий эксперимент после управляемой паузы и продолжения.
Он проверяет весь путь: callbacks тестового плагина используют принадлежащую ему
область → запрос отключения → подтверждение QEMU → обнуление → munmap → выгрузка
библиотеки → следующая точка того же гостя с сохранёнными стеком и FD.

В этой версии освобождается собственная область нового тестового плагина.
Существующий `libtaintforge_ir.so` не отключается и его память не освобождается.
Файлы Phase 1, `probe.c`, `guest.S` и заголовок QEMU не изменяются.
Поддерживается только поставляемый однопоточный i386 ELF и QEMU 11.0.1/API 6.
Реальное исполнение нового сценария QEMU в среде разработки не выполнено;
host-проверки и остающаяся VM-приёмка перечислены ниже.

**Почему следующий шаг именно такой.** Предыдущий эксперимент доказал возможность
остановить гостевой поток в callback и продолжить его без пересоздания процесса.
Для освобождения памяти дополнительно нужно исключить вызов callbacks со старыми
указателями. Простого `free()` во время паузы недостаточно: QEMU может хранить эти
указатели в уже переведённом коде. Новый плагин специально передаёт указатель
на свою mmap-область как `userdata` каждого instruction callback.

В исходниках именно QEMU v11.0.1 проверена следующая цепочка:

- `qemu_plugin_uninstall(id, callback)` вызывает `plugin_reset_uninstall()`.
- При наличии текущего vCPU работа ставится через `async_safe_run_on_cpu()`.
- `plugin_flush_destroy()` очищает переведённый код, затем выполняет удаление.
- `plugin_reset_destroy__locked()` удаляет callbacks и контекст плагина,
  вызывает переданный callback и только после его возврата вызывает `g_module_close()`.

Следовательно, возврат из `qemu_plugin_uninstall()` не означает завершения
отключения. Вызвавший его instruction callback должен вернуть управление QEMU.
Ожидание подтверждения внутри этого же callback мешало бы обработке safe work.
Подтверждающий callback также ещё не доказывает выгрузку `.so`: её отдельно
проверяет внешний контроллер во второй точке исполнения.

**План и его реализация.** Работа ограничена одним экспериментом, без новой системы
плагинов, универсального аллокатора, RSP, checkpoint и изменений production runner.

| Шаг | Реализовано | Проверка |

В C функции расположены по жизненному циклу:

- `qemu_plugin_install()` проверяет профиль/параметры, создаёт область и журнал,
  регистрирует init/translation/exit callbacks. Ошибка установки не запрашивает uninstall.
- `init_vcpu()` отвергает дополнительный vCPU.
- `translate()` регистрирует `count_exec()` для инструкций и callbacks двух точек.
- `count_exec()` обновляет рабочие счётчики через указатель на область. В состоянии
  REQUESTED данные всё ещё доступны; счётчик pending фиксирует такие вызовы.
- `boundary()` однократно запрашивает uninstall на первой точке. В режиме keep
  записывает пропуск отключения и продолжает наблюдение.
- `removed()` подтверждает порядок, сохраняет счётчики, обнуляет 4 МиБ через
  volatile stores, проверяет все нулевые байты, снимает отображение вместе с
  guard pages и закрывает свой FD журнала. Никаких QEMU CPU/memory API здесь нет.
- `second_point()` позволяет контрольному режиму keep доказать продолжение наблюдения.
- `retained_exit()` допускается только в keep. Выход обычного режима без
  подтверждённого отключения считается ошибкой.

У тестового плагина нет собственных потоков, таймеров, обработчиков сигналов
или сторонних callback-регистраций. Поэтому в этом эксперименте QEMU управляет
всеми вызовами его кода. На настоящий анпакер эту предпосылку автоматически
переносить нельзя: требуется отдельная проверка каждого источника вызовов.

В Python:

- `validate_lifecycle()` проверяет последовательность событий, PID, неизменность
  описания области, размеры/выравнивание и счётчики отложенных callbacks.
- `parse_maps()`, `file_mapped()`, `covered()`, `inspect_memory()` разбирают
  отображения, сопоставляют `.so` по устройству/inode и проверяют границы/права.
- `RetirementGate` вызывается существующим контроллером после двух снимков и
  проверенного удержания, до CONTINUE. При ошибке соединение закрывается,
  следующая команда продолжения не отправляется.
- `verify_result()` после завершения повторно проверяет сохранённые maps,
  их хеши, префиксы журнала, порядок наблюдений и гостевые снимки.
- `build()` переиспользует сборку прежнего probe/ELF и собирает дополнительный `.so`.
- `suite()` переиспользует `run_case()`: запуск процессов, таймауты, оригинальный
  протокол, stack/FD oracle и проверку Phase 1 не продублированы.

**Ход успешного исполнения.** Один сценарий создаёт один QEMU. Контроллер и
гостевые точки работают так же, как в предыдущем probe. В варианте совместной
загрузки одновременно работают Phase 1, постоянный capsule observer и временный
retirement plugin.

1. Новый плагин резервирует `4 МиБ + 2 * page_size`, первоначально PROT_NONE.
   Средние 4 МиБ становятся RW без execute. Область заполняется `0xa7`, затем
   инициализируются счётчики; это касается всех страниц, а не только адресного резерва.
2. Гость открывает FD, пишет `before`, готовит стек и первую точку.
3. Observer удерживает vCPU. Контроллер видит сохранённую область с guard pages,
   загруженную библиотеку и правильные регистры/буфер/стек.
4. В зависимости от порядка callbacks запрос uninstall уже поставлен или будет
   поставлен сразу после CONTINUE 1. Во время первого удержания область ещё жива.
5. Observer возвращается. QEMU обрабатывает запрос через safe work. Возможные
   callbacks до подтверждения продолжают обращаться к живой области.
6. Подтверждение вызывает обнуление/munmap. QEMU закрывает библиотеку после возврата.
7. Гость пишет `between`, меняет буфер и достигает второй точки. Контроллер проверяет
   исчезновение адресного диапазона и `.so`, наличие observer и, где загружена, Phase 1.
8. После CONTINUE 2 гость проверяет стек/позицию FD, пишет `after`, читает все 21 байт,
   возвращается из функции и печатает `CAPSULE_OK`. QEMU завершается с кодом 0.

Порядок событий освобождения строгий:

`arena_allocated → uninstall_requested → callbacks_removed → arena_zeroed → arena_unmapped`.

Событие `arena_unmapped` записывается после успешного munmap. Отсутствие библиотеки
проверяется по maps позже; собственное событие выгрузки из уже выгруженной `.so`
невозможно. `.so` зависимости, используемые другими компонентами, могут остаться.

CONTINUE 1 разрешает QEMU обработать отложенную работу и гостю двигаться дальше.
Эксперимент не гарантирует ноль гостевых инструкций между запросом отключения и
его подтверждением. Он требует, чтобы освобождение завершилось до наблюдения
второй точки. Атомарное переключение фаз точно на произвольном OEP этим не доказано.

**Что доказывается о памяти.** В первой точке требуется покрытие всего диапазона
guard/RW/guard; допускается объединение соседних VMAs с одинаковыми правами.
Во второй точке требуется отсутствие любого пересечения с прежним диапазоном и
отсутствие file-backed отображений конкретной `.so`. Устройство и inode фиксируются
до запуска QEMU, чтобы не полагаться на видимое имя или позднюю замену файла.
После успешного сценария дополнительно сверяются хеши обеих тестовых `.so` и ELF.

Проверка диапазона консервативна: если другой компонент успел заново занять те же
адреса, сценарий выдаст ошибку `still mapped or was reused`. Это не утверждение,
что старый плагин оставил утечку. Для данного фиксированного workload такой исход
нужно разбирать по сохранённой карте, а не принимать как успешное освобождение.

RSS не является критерием успеха. Он меняется из-за QEMU, TCG, libc и Phase 1;
его снижение не доказывает освобождение нужного владельца. Контроллер читает
только `/proc/PID/maps`, а не произвольную гостевую память из внешнего потока.
Гостевые регистры и память по-прежнему читает неизменённый `probe.c` в допустимом callback.

Это не квота памяти, не защита одного native-плагина от другого и не доказательство
отсутствия всех следов анализа. Статические поля `.so`, общие библиотеки, heap allocator,
журналы и состояние QEMU имеют разные жизненные циклы. Ни cgroup/RLIMIT, ни
универсальный Memory Provenance/Residue Oracle этим шагом не вводятся.
`phase1_detached`, `phase1_memory_released`, `memory_isolation`, `residue_free`,
`whole_qemu_stop` остаются false. Поле `test_plugin_unloaded=true` относится только
к библиотеке `libcapsule_retire.so`.

QEMU использует свой safe-work механизм для удаления callbacks. Первая наблюдаемая
пауза capsule по-прежнему означает ожидание одного гостевого vCPU, а не общую
остановку QEMU и анализатора. Продолжение не восстанавливает процесс из снимка.

**Применение.** Распаковать `taintforge_capsule_retirement_v1.zip`. Проверка
установщика выбирает совместимую базу standalone-v1 или capsule-unified-v1 по
содержимому файлов; несовпадение commit ID само по себе не является ошибкой.
Неизвестные локальные изменения не перезаписываются. Резервная копия создаётся
в `workdir/capsule-retirement-backup-*`. Набор замен не является транзакцией,
устойчивой к отключению питания; обычные ошибки записи вызывают откат своих замен.

```bash
cd "$HOME/taintforge"
retirement_kit_dir="$(mktemp -d)"
unzip "$HOME/Downloads/taintforge_capsule_retirement_v1.zip" -d "$retirement_kit_dir"
python3 "$retirement_kit_dir/taintforge_capsule_retirement_v1/apply.py" --repo . --check
python3 "$retirement_kit_dir/taintforge_capsule_retirement_v1/apply.py" --repo . --apply
```

Архив также содержит два обычных патча: основной `taintforge_capsule_retirement_v1.patch`
для capsule-unified-v1 и `taintforge_capsule_retirement_standalone_v1.patch` для
исходного standalone. Они дают тот же результат, что соответствующая ветка установщика.
Не применять патч поверх уже успешно применённого установщика.

**Первый запуск на VM.** Используются уже установленные gcc/binutils/pkgconf/glib2/Python.
Новых пакетов и sudo для этого standalone-эксперимента не требуется. Это запуск
контрольного ELF, не sandbox для произвольного malware; `--binary` отсутствует.

```bash
cd "$HOME/taintforge"
retirement_out="workdir/capsule-retirement-$(date +%Y%m%d-%H%M%S)"
python3 -m experiments.execution_capsule_retire.controller \
  --repo . --qemu /usr/bin/qemu-i386 \
  --phase1 build/libtaintforge_ir.so \
  --case observer-first --out "$retirement_out"
```

Ожидается `observer-first: passed`, QEMU exit 0, `supervisor_kill=false`, четыре
снимка и `retirement.owned_arena_released=true`. Во второй карте нет области и
retirement `.so`, а stdout и контрольный файл совпадают с прежним экспериментом.
Путь к Phase 1 нужен preflight даже для сценариев, где она не загружается.

**Полная VM-матрица.** Каждый сценарий создаёт отдельный процесс QEMU; внутри
сценария обе точки принадлежат одному продолжающемуся процессу.

```bash
cd "$HOME/taintforge"
retirement_suite_out="workdir/capsule-retirement-suite-$(date +%Y%m%d-%H%M%S)"
python3 -m experiments.execution_capsule_retire.controller \
  --repo . --qemu /usr/bin/qemu-i386 \
  --phase1 build/libtaintforge_ir.so --out "$retirement_suite_out"

python3 - "$retirement_suite_out/report.json" <<'PY'
import json
import sys
with open(sys.argv[1]) as stream:
    report = json.load(stream)
print("Итог:", report["status"])
for case in report["cases"]:
    memory = case.get("retirement", {})
    print(case["retirement_case"], case["status"],
          "qemu_exit=", case.get("qemu_exit"),
          "released=", memory.get("owned_arena_released"),
          "unloaded=", memory.get("test_plugin_unloaded"),
          "supervisor_kill=", case["supervisor_kill"],
          "error=", case.get("error", ""))
if "error" in report:
    print("Ошибка комплекта:", report["error"])
PY
```

| Сценарий | Порядок или вмешательство | Ожидаемый результат |
|---|---|---|
| `owner-first` | retirement, observer | Освобождение и продолжение |
| `observer-first` | observer, retirement | То же при обратном порядке |
| `phase1-first` | Phase 1, observer, retirement | Освобождение тестового владельца; Phase 1 остаётся отображённой и проходит прежнюю проверку финализации |
| `owner-phase1-first` | retirement, Phase 1, observer | Совместная загрузка с владельцем первым |
| `keep-control` | Observer и владелец без запроса uninstall | Гость успешен; область и `.so` сохраняются во второй точке |
| `timeout-1`, `timeout-2` | Контроллер не разрешает продолжение | Exit 124; до освобождения и после него соответственно |
| `disconnect-1`, `disconnect-2` | Контроллер закрывает соединение | Exit 125; тот же порядок |
| `kill-controller-1`, `kill-controller-2` | Контроллер получает SIGKILL | Exit 125; тот же порядок |

Во всех шести аварийных сценариях также загружается Phase 1. Её финальный экспорт
после `_exit()` не ожидается, но проверяется свидетельство instruction callback.
Эта прежняя проверка подтверждает факт работы Phase 1 в запуске; сама по себе она
не доказывает её активность на каждой инструкции после отключения тестового плагина.
Успешный отрицательный тест означает ожидаемую аварию, а не успешное гостевое
завершение. В keep-control `released=false` и `unloaded=false` — правильный результат.
Любой fallback kill supervisor считается провалом теста.

Ранее проверенный observer остаётся загруженным после retirement. Именно его
watchdog завершает QEMU при потере контроллера/таймауте. В удаляемом плагине
собственного watchdog-потока нет: поток с кодом из выгруженной `.so` был бы опасен.
Пауза ограничена 5 с, общий бюджет observer — 30 с; удержание — 200 мс.
При внутренней ошибке retirement plugin завершает весь процесс кодом 127 и
диагностикой `RETIRE_ABORT`. Такая ошибка не принимается за успешное освобождение.

В корне `--out` находятся `report.json` и `build/build.json` с версиями, адресами
символов и хешами исходников/бинарников. Карты содержат адреса процесса и локальные
пути; это диагностические артефакты данного контролируемого запуска.

**Проверки в среде разработки.** Точные результаты и журналы входят в
`LOCAL_VALIDATION.md`, `LOCAL_VALIDATION.json`, `validation/` архива. Host harness
подставляет регистрацию callbacks и асинхронную очередь QEMU, но реально выполняет
выделение, защиту, заполнение, проверку нулей, unmap, dlopen и dlclose.
Проверка с санитайзерами не превращает модель в QEMU-приёмку.

На VM host-тесты можно повторить обычным установленным toolchain:

```bash
cd "$HOME/taintforge"
python3 -m unittest discover -s experiments/execution_capsule_retire/tests -v
```

Реальная обработка `async_safe_run_on_cpu`, очистка TCG, порядок callbacks двух
плагинов, Phase 1 после flush, stack/FD oracle и отказоустойчивость всей новой
связки остаются предметом приведённой VM-матрицы. Этот комплект не подключает
retirement к production unified handoff до такой проверки.

**Следующий контракт с разработчиком Phase 1.** После успешной VM-приёмки будет
проверен механизм, но анпакер ещё нужно сделать готовым к живому отключению:

1. В допустимом vCPU-контексте получить необходимые гостевые данные и завершить
   выбранный экспорт. Прекратить добавление новых аналитических задач.
2. Подготовить завершение собственных потоков/очередей/внешних callbacks, если они
   есть. Не ждать задач, которым нужны удерживаемые внутренние блокировки QEMU,
   из uninstall completion: в проверенной версии он вызывается под plugin lock.
3. Запросить uninstall собственного plugin ID и вернуть управление backend.
4. После подтверждения освободить принадлежащие анализатору структуры и закрыть
   принадлежащие ему FD. Обычный atexit callback при uninstall удаляется вместе
   с остальными; полагаться на его будущий запуск для cleanup нельзя.
5. Проверить освобождение по учёту владельца и продолжение гостя. Общие зависимости
   QEMU и других плагинов не считать принадлежащими только Phase 1.

В просмотренной Phase 1 финальный экспорт и освобождение связаны с `plugin_exit()`;
есть GLib hash tables, массивы, instruction contexts, trace/aux buffers и Capstone.
Они не находятся автоматически в одной mmap-области. Вызвать текущий cleanup
посреди исполнения или внешне выгрузить `.so` без этого контракта нельзя считать
безопасным решением. Данный патч не переносит и не меняет этот код.
